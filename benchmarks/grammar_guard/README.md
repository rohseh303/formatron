# GrammarGuard adversarial-schema benchmark

Inference servers that accept user-supplied JSON schemas must turn pathological
schemas into **fast, structured rejections** instead of hangs, out-of-memory
kills or crashes, while ordinary schemas compile quickly and always yield
schema-valid output.  This benchmark measures exactly that for the hardened
kbnf + Formatron stack and compares it with the unlimited default
configuration and with two other constrained-decoding engines (XGrammar and
llguidance).

Results of the last full run are in [`RESULTS.md`](RESULTS.md) (generated by
`report.py`; pass `--analysis notes.md` to append a hand-written findings section).

## Layout

| file | purpose |
| --- | --- |
| `corpus.py` | deterministic, seeded generator for **1,078 schemas** (610 normal / 468 adversarial) in 30 families |
| `vocab.py` | the synthetic ~3k-token byte vocabulary shared by every engine, plus the real-tokenizer vocabulary pickling used by `--tokenizer` |
| `worker.py` | what runs *inside* the isolated child: admission, compile, random walk, validation |
| `runner.py` | process pool: one `spawn` child per schema, hard wall-clock kill, RSS watchdog, resumable JSONL |
| `report.py` | aggregates `results/*.jsonl` into `RESULTS.md` |
| `results/` | `hardened.jsonl`, `default.jsonl`, `xgrammar.jsonl`, `llguidance.jsonl` (synthetic vocabulary, one record per schema); `hardened-<vocab>.jsonl`, `default-<vocab>.jsonl` and `vocab-<vocab>.pkl` for real-tokenizer runs |
| `../../tests/test_grammar_guard_bench.py` | fast smoke test of corpus, worker, runner and report (incl. the tokenizer path when `transformers` and the cached tokenizer are available) |

## Running

```bash
source ../.venv/bin/activate            # python 3.11 with the kbnf fork, formatron fork, xgrammar, llguidance
cd formatron

python -m benchmarks.grammar_guard.corpus --stats            # family counts
python -m benchmarks.grammar_guard.corpus --show adv/wide_enum/0002
python -m benchmarks.grammar_guard.corpus --dump /tmp/corpus.jsonl   # materialised corpus (large, never committed)

# kbnf + Formatron, hardened admission policy (admit_json_schema + build(hardened=True))
python -m benchmarks.grammar_guard.runner --config hardened
# kbnf + Formatron, stock unlimited path (create_schema + build())
python -m benchmarks.grammar_guard.runner --config default --mem-mb 3072
# differential compile check with the other engines
python -m benchmarks.grammar_guard.runner --engines xgrammar,llguidance

python -m benchmarks.grammar_guard.report                    # -> RESULTS.md
```

### Running on a real tokenizer vocabulary

```bash
# same two kbnf configs, but with Qwen2.5's 151,665-token vocabulary (needs transformers + the tokenizer in the HF cache)
python -m benchmarks.grammar_guard.runner --config hardened --tokenizer Qwen/Qwen2.5-0.5B-Instruct --workers 4 --timeout 20 --no-resume
python -m benchmarks.grammar_guard.runner --config default  --tokenizer Qwen/Qwen2.5-0.5B-Instruct --workers 4 --timeout 20 --no-resume
python -m benchmarks.grammar_guard.report      # RESULTS.md gains a "Real vocabulary (Qwen2.5, 151k tokens)" section
```

What `--tokenizer <hf-id>` changes:

- The parent loads the Hugging Face tokenizer **once**, builds the `kbnf.Vocabulary` exactly
  as `formatron.integrations.transformers.create_engine_vocabulary` does (byte-level BPE
  `Ġ`/`Ċ` mangling and sentencepiece `▁` undone by `get_original_characters`), and pickles the
  raw `{id: bytes}` / `{id: str}` maps to `results/vocab-<name>.pkl` (4.5 MB for Qwen2.5).
  `kbnf.Vocabulary` is not picklable and `import transformers` is slow, so each spawned child
  unpickles the maps (~20 ms) and rebuilds the vocabulary (~70 ms, reported as `vocab_load_ms`,
  outside every compile timing).  An existing pickle is reused when it was built from the same
  tokenizer id (`--rebuild-vocab` forces a rebuild, `--vocab-file` points elsewhere).
- The random walk samples from the real allowed-token set and appends the **real token bytes**,
  so completed documents are what a model using that tokenizer could emit; `decode` uses the
  same bytes.  The walk's own bookkeeping cost (materialising a ~100k-id allowed list and the
  biased sampling, ~3 ms/step) is recorded as `generation.walk_overhead_ms` and is not part
  of `mask_ms`/`accept_ms`.
- Results go to `results/<config>-<name>.jsonl` (`hardened-qwen2.5.jsonl`,
  `default-qwen2.5.jsonl`; `<name>` defaults to the model family derived from the id, e.g.
  `qwen2.5`, override with `--vocab-name`), so the synthetic runs are never overwritten.  Every
  row carries `vocab` (`name`, `tokenizer`, `size`) and the run `options` (timeout, workers,
  memory cap, token cap), which the report uses to label the section.
- Engine construction (`compile_ms` = `FormatterBuilder.build` = `kbnf.Engine(...)`) is
  vocabulary-dependent; admission, `create_schema` and grammar generation are not.  Expect
  compile p50 to grow from ~10 ms to a few hundred ms and the long tail (enum-heavy and
  pattern/length-heavy schemas) to grow by 50–100×, which is why the real-vocabulary runs use
  `--timeout 20`.
- Only the kbnf configs support `--tokenizer`; `--engines xgrammar,llguidance` keep using the
  synthetic vocabulary (the runner refuses the combination).

Useful runner flags: `--timeout 10` (seconds, child is SIGKILLed on expiry),
`--mem-mb 4096` (parent-side RSS watchdog plus best-effort `RLIMIT_AS`/`RLIMIT_DATA`
inside the child; macOS ignores the rlimits, the watchdog still works), `--workers 6`,
`--token-cap 512`, `--family F` (repeatable), `--category normal|adversarial`,
`--ids a,b,c`, `--per-family N`, `--limit N`, `--no-resume`.  Runs are resumable:
ids already present in the JSONL are skipped, so an interrupted run can simply be
restarted.  Every schema runs in a *fresh* child so a crash, hang or OOM in one schema
can never poison another measurement; the price is ~0.7 s of interpreter start-up per
schema, which is why `wall_ms_parent` is much larger than the in-child timings.

## What is measured

Per schema and configuration (`results/<config>.jsonl`, one JSON object per line):

- `outcome`: `admitted`, `rejected`, `timeout` (killed at the wall-clock limit),
  `crash` (child died: signal, e.g. segfault), `oom` (RSS watchdog kill).
- `reason`: structured; for limit rejections `kind` is `schema_limit` (Formatron
  `SchemaLimits`), `grammar_limit` (kbnf `GrammarLimits`) or `decode_limit`
  (kbnf `DecodeLimits`) with `limit_phase`, `resource`, `observed`, `limit`, `path`
  parsed from the engine's message
  (`grammar resource limit exceeded during {phase}: {resource} observed {observed}, limit {limit}`).
  Other kinds: `unsupported_schema`, `invalid_schema`, `kbnf_parse_error`,
  `regex_limit`, `recursion_error`, `memory_error`, `engine_error`, `python_exception`.
- `phase_reached`: the last progress message the child sent before it finished or was
  killed (`admission`, `create_schema`, `grammar_gen`, `compile`, `inspect`,
  `generate:N`), so a timeout is attributed to a phase.
- timings in ms: `admission_ms` (hardened only: `admit_json_schema`, i.e. schema
  limits + conversion + grammar generation + full hardened `check_grammar`),
  `create_schema_ms`, `grammar_gen_ms`, `schema_to_grammar_ms`, `compile_ms`
  (`FormatterBuilder.build` = `kbnf.Engine` construction with the vocabulary),
  `wall_ms` (in child), `wall_ms_parent` (including spawn).
- `grammar_bytes`, `inspect` (kbnf `inspect_grammar` complexity report),
  `admission.schema_complexity` / `admission.grammar_complexity`.
- `generation` (kbnf configs, admitted schemas): biased random walk with the run's
  vocabulary, capped at 512 tokens: `tokens`, `completed`, `hit_token_cap`, `error`,
  per-step `mask_ms` and `accept_ms` percentiles, `walk_overhead_ms` (harness cost outside
  the engine), `allowed_mean`, Earley chart peaks (`chart_peak_newest`, `chart_peak_total`),
  `cache_peak`, `output_valid` (`json.loads` + `jsonschema.Draft202012Validator` against the
  *original* schema), `validation_error`, `output_preview`.
- `vocab` (`name`, `tokenizer`, `size`), `vocab_load_ms`, `vocab_size`, `options` (the
  runner's timeout / memory cap / token cap / workers / seed).
- `peak_rss_mb` (child `ru_maxrss`), `peak_rss_mb_observed` (watchdog), `exitcode`.

For XGrammar (`Grammar.from_json_schema` + `GrammarCompiler.compile_grammar`) and
llguidance (`LLMatcher.grammar_from_json_schema` + `LLMatcher(...)`) only the compile
path is measured, under the same isolation, timeout and memory cap.  llguidance ships
with its own default parser limits; XGrammar has none.

## What `expect` means

Every spec carries an expectation that the report uses to decide what is a defect:

- `admit` — a realistic schema.  A rejection is a **false positive** and is listed with
  the resource that fired so the limit can be re-tuned.
- `reject` — a resource attack no bounded engine should accept (e.g. `maxItems: 10^9`,
  a 100k-member enum, an 8 MB `const`).  Admitting it is not a bug by itself, but the
  engine must not hang, crash or exhaust memory doing so.
- `either` — a bounded engine may reasonably accept or reject (e.g. 12 optional
  properties, a 2,000-member enum, `(a+)+`).  The only requirements are no
  hang/crash/OOM and, if admitted, the output must validate.

## Families

Normal (610): `flat_object`, `nested_object`, `array_of_objects`, `enum_fields`,
`enum_medium` (64–512 members), `optional_fields` (1–16 optional properties),
`anyof_union`, `numeric_bounds`, `numeric_bounds_nonzero`, `string_length`, `patterns`
(email, ISO dates, UUID, IPv4, …), `refs_defs`, `recursion` (trees, linked lists,
expression ASTs, comment threads), `tuples` (`prefixItems`), `mixed_realistic`
(order, user profile, event log, GeoJSON feature, chat message, invoice, …).

Adversarial (468): `deep_nesting` (50–2000 levels, object/array/anyOf chains),
`wide_enum` (2k–100k members, str/int/mixed/unicode), `giant_const` (64 KB–8 MB literals,
keys, nested consts), `huge_items` (`minItems`/`maxItems` up to 10^9, spans,
2000-element `prefixItems`), `huge_string_length` (`minLength`/`maxLength` up to 10^8),
`regex_nested_quantifiers` (`(a+)+`, `(a|aa)+`, …), `regex_counted_repetition`
(`.{1000,5000}`, `(a{1,1000}){1,1000}`, `x{100000}`), `regex_alternation_blowup`
(50k-way alternations, `(cat|car|cart…){1,100000}`, `\p{L}` classes),
`many_optional_props` (12–64 optional properties: exponential in Formatron's encoding),
`thousands_of_props` (1k–20k properties), `recursive_ref_fanout` (mutual recursion,
fan-out 30), `unicode_heavy` (CJK/emoji/ZWJ/RTL keys, enums, consts, patterns),
`hostile_literals` (quotes, backslashes, control characters, `$ref`-looking keys,
huge floats), `mixed_combo` (combinations), `grammar_injection` (property names, enum
values and patterns that try to break out of KBNF quoting).

## Caveats

- **Synthetic vocabulary by default.**  `vocab.py` is a hand-built ~3k-token byte vocabulary
  (all single bytes, JSON punctuation, numbers, common words, the corpus's key names,
  a few multi-byte UTF-8 tokens), not a real BPE tokenizer.  Absolute per-token mask
  latencies from those runs are therefore not comparable with a 32k–152k vocabulary — only
  relative comparisons (hardened vs default, family vs family) are meaningful.  Engine
  construction cost in kbnf is vocabulary-dependent, so real vocabularies make the
  "admitted but slow" cases *worse*, not better; the `--tokenizer` runs in `RESULTS.md`
  quantify this (the synthetic sections and the real-vocabulary section are paired on the
  same schema ids).
- **Pattern strings are matched on raw JSON text.**  Formatron encodes `pattern` as
  `"(?:<regex>)"`, so a regex that admits `"`, `\` or control characters (`.`,
  `[^a]`, `\s`, …) lets the engine accept unescaped ones inside the string and the
  document is not valid JSON.  With the synthetic vocabulary such walks usually hit the
  token cap before finishing; with a real vocabulary (long tokens, lots of raw punctuation
  tokens) they complete and show up as `json: Invalid control character` /
  `Expecting ',' delimiter` in the invalid-output lists.  This is an engine-side fidelity
  gap, not a walk artifact: a model can emit those tokens too.
- **Random walk, not a model.**  Tokens are sampled from the allowed set with a bias
  toward finishing (openers are suppressed and closers boosted as the 512-token budget
  is consumed).  Strings therefore contain word salad and the walk can hit the token
  cap on schemas that legitimately need >512 tokens (`minItems: 1000`,
  `.{1000,5000}`); those are reported as `hit_token_cap`, not as failures.
- **Validation is against the original schema** with `jsonschema`.  A completed walk
  whose output fails validation is either a Formatron grammar bug or a vocabulary
  artifact; `RESULTS.md` separates the two.
- Timings were taken on a shared machine with 6 child processes in parallel;
  treat p99 values as indicative.
